# 对外 API 文档模板

> **指导性模板**：本文件整篇会作为参考喂给模型。生成「对外 API 对接文档」时，请**严格参照**下面的章节结构、表格规范与写作风格来组织内容。
> 具体事实（域名、路径、字段、错误码、签名规则等）一律**以知识库为准**——模板只决定"长什么样"，不提供事实。知识库中没有的内容不要编造。

## 写作总则

- 面向**外部接入方**，语气专业、准确，能让对方照着直接完成对接。
- 凡是可枚举的东西都用**表格**：接口总览、字段说明、错误码。
- 所有请求/响应示例都用**代码块**：JSON 用 ```json```，HTTP 头用 ```http```，其它固定文本用 ```text```。
- 环境相关的值用**占位符**：如 `{base_url}`、`<access_token>`、`<hex string>`。
- **字段表**统一四列：`字段 / 类型 / 必填 / 说明`（纯响应字段可省"必填"，用三列 `字段 / 类型 / 说明`）。
- **错误码表**统一列：`code / message`（或 `type`）`/ HTTP / 说明`。
- 术语、大小写、路径写法全程保持一致；复用的数据结构（如 token 结构）集中定义一次，后面引用即可。

## 文档结构（严格按此顺序）

### 一、文档信息

开头放一张元信息表：

| 文档项 | 内容 |
| --- | --- |
| 文档名称 | … |
| 面向对象 | 谁来对接（接入方） |
| 接口提供方 | … |
| 版本 | vX.Y |
| 状态 | 草稿 / 发布 |

### 二、背景

用 2–3 段说明：业务背景、参与方、整体数据流（谁调用谁、鉴权凭证从哪来、到哪结束）。让读者先建立全局认知，再看接口。

### 三、接口总览

一张表列出**全部**接口：

| 序号 | 接口 | 调用方 | 路径 | 鉴权 |
| --- | --- | --- | --- | --- |
| 1 | … | 服务端 / 客户端 | `METHOD /path` | 签名 / Bearer / 无 |

表格下用要点补充：路径命名规则、`{base_url}` 含义、哪些接口需要登录态、云云对接与客户端对接的边界等。

### 四、通用约定

集中定义所有接口共用的规则，避免在每个接口里重复：

- **协议与格式**：请求协议（HTTPS）、请求方式、`Content-Type`、字符编码。
- **统一响应格式**：给出标准响应信封并配字段表，例如：

  ```json
  { "code": 0, "message": "success", "data": {} }
  ```

- **鉴权**：
  - Bearer token 的请求头写法与含义；
  - 若存在**签名鉴权**，写清：需要的 Header、待签名字符串的拼接顺序与分隔符、签名算法（如 HMAC-SHA256）、body 的序列化规则（key 字典序、紧凑格式、空 body 约定）。
- **关键数据结构**：把被多个接口复用的结构（如 `access_token` / `refresh_token` 双 token 及其过期时间戳）在这里定义一次。

### 五、对接流程

用**编号步骤**描述端到端时序：从登录 / 换取凭证 → 调用业务接口 → 凭证过期后刷新。让接入方清楚调用先后顺序和依赖关系。

### 六、接口详情

每个接口用**统一的小节模板**，字段顺序保持一致：

- **路径**：`METHOD {base_url}/path`
- **调用方**：服务端 / 客户端
- **鉴权方式**：Bearer / 平台签名 / 无
- **请求头**（```http``` 代码块）
- **请求体**（```json``` 示例 + 字段表 `字段/类型/必填/说明`；无请求体则注明）
- **成功响应**（```json``` 示例 + 字段表 `字段/类型/说明`）
- **失败 / 特殊响应**（如未命中、配额不足等，给出示例）
- **业务说明**（要点式：边界条件、注意事项、副作用、与其它接口的关系）
- **常见错误**（错误码表）

### 七、回调接口（如有）

若存在反向回调（由对方实现、本方调用），单独成节，写清：路径、接口提供方、鉴权 / 签名规则、请求体（含加密字段约定）、成功回执格式、以及"成功仅表示已接收"这类语义边界。

### 八、错误码总表

最后集中列出全部错误码，便于查阅：

| Code | Name | HTTP | Meaning |
| --- | --- | --- | --- |
| `0` | `OK` | `200` | 通用成功码 |

并注明特殊约定（如保留区间、某些码虽 `code!=0` 但视为成功、网关类接口错误格式与业务错误格式不同等）。

## 接口详情填写范例（对齐格式用）

> 下面是"六、接口详情"里单个接口应有的样子，仅示范格式，内容以知识库为准。

### X.Y 示例接口名

一句话说明该接口做什么。

**路径**：`POST {base_url}/path/to/api`

**调用方**：客户端

**鉴权方式**：`Authorization: Bearer <access_token>`

**请求头**：

```http
Authorization: Bearer <access_token>
Content-Type: application/json
```

**请求体**：

```json
{ "foo": "bar" }
```

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `foo` | string | 是 | 示例字段说明 |

**成功响应**：

```json
{ "code": 0, "message": "success", "data": { "result": 1 } }
```

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `result` | int | 示例返回字段 |

**业务说明**：

- 要点一。
- 要点二。

**常见错误**：

| code | message | HTTP | 说明 |
| --- | --- | --- | --- |
| `3004` | `USER_AUTH_FAILED` | `200` | token 缺失、无效或过期 |
| `5006` | `INTERNAL_ERROR` | `500` | 未归类内部错误 |
